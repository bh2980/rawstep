# Rawstep — Design Language & Screen Direction

UI 디렉터가 정리한 대시보드 디자인 언어와 화면 방향입니다. 대시보드 UI를 바꿀 때 이 문서를 기준으로 삼습니다.

## 1. Product Definition

Rawstep은 테스트 결과 대시보드가 아니다.
스크린리더 사용자가 목표까지 이동한 경로를 기록하고, 사람이 병목의 근거를 조사할 수 있게 만드는 행동 추적 도구다.
Rawstep이 보여 주어야 하는 것은 결론이 아니라 흔적이다.

```
Goal
 ↓
Perception
 ↓
Action
 ↓
Page response
 ↓
Next action
 ↓
…
 ↓
Outcome
```

따라서 제품의 핵심 질문은 "통과했는가?"가 아니라, "어디에서 경로가 길어졌고, 그때 페이지와 모델에 각각 무슨 일이 있었는가?"다.

## 2. Design Concept

**RAW TRACE — Trace Analysis Instrument**

Rawstep의 디자인은 일반적인 SaaS Dashboard보다 다음 세 가지에서 가져온다: 실행 추적기, 진단 장비, 조사 기록지. 단, 실제 비행기 계기판이나 오실로스코프를 흉내 내지는 않는다. 그들이 정보를 다루는 방식을 가져온다.

핵심 문장: **판정하지 않고, 경로를 남긴다.**

시각 언어의 핵심은 세 단어다.

- **TRACE** — 무엇이 어떤 순서로 일어났는가.
- **EVIDENCE** — 그 판단을 뒷받침하는 실제 화면·발화·행동·변화는 무엇인가.
- **SOURCE** — 그 현상이 페이지에서 관찰된 것인지, 모델의 판단 과정에서 생긴 것인지.

## 3. Design Principles

### 3.1. Outcome보다 Path

목표 도달 여부는 중요한 정보지만 화면의 주인공이 되어서는 안 된다. `PASS` / `FAIL`처럼 크게 표시하는 테스트 러너 UI를 피한다. 대신 다음을 보여 주고, 바로 아래에서 어떤 요소에서 경로가 늘어났는지 읽을 수 있게 한다.

```
목표 도달     2 / 3
보통 행동 수  12
가장 빠름     10
```

### 3.2. Evidence before Interpretation

Rawstep은 `사실 → 근거 → 사람의 판단` 순서를 지킨다. AI가 "이 버튼은 접근성 문제가 있습니다."라고 결론 내리는 인터페이스를 만들지 않는다. 대신 판단 재료를 제공한다.

```
버튼 · 결제하기

3번 중 2번
키보드 포커스가 페이지 밖으로 이동했습니다.

실행 #12 · 행동 7
실행 #14 · 행동 9
```

### 3.3. Element is the Unit

분석의 최소 단위는 내부 이벤트나 힌트 타입이 아니라 사용자가 만나는 페이지 요소다. 역할과 accessible name을 하나의 `Element Identity`로 취급한다. 같은 요소에 관련된 여러 실행과 여러 현상은 가능한 한 함께 묶는다.

```
BUTTON
결제하기

DIALOG
배송지 변경

STATUS
결제가 완료되었습니다
```

## 4. 가장 중요한 위계

화면의 정보는 항상 다음 순서로 강도가 낮아진다.

1. 목표와 현재 맥락
2. 관찰된 사실
3. 페이지에서 관찰된 현상
4. 모델 행동 / 불확실성
5. 원본 기록

특히 페이지 현상과 모델 행동을 같은 카드 스타일로 만들지 않는다. 이 둘은 단순히 `solid border / dashed border` 수준보다 더 크게 분리한다.

## 5. Page Evidence vs Model Behavior

**Page Evidence** — 페이지에서 실제로 관찰된 현상. 시각적으로 단단한 영역으로 표현한다.

```
PAGE

BUTTON
결제하기

키보드 포커스가 페이지 밖으로 이동했습니다.

2 / 3 executions
#12   #14
```

특징: solid border, 명확한 왼쪽 rail, element identity 강조, 실행 증거 바로 연결, 높은 visual weight.

**Model Behavior** — 시뮬레이션한 사용자(계획 모델의 계획)가 돌아가거나 일찍 멈춘 현상. 별도의 보조 layer로 다룬다.

```
MODEL BEHAVIOR

BUTTON
결제하기

이 요소와 다른 버튼 사이를 반복해서 이동했습니다.

실행 2회
추정
```

특징: surface를 만들지 않거나 아주 약하게 사용, open marker, inset layout, `모델 행동` source label 항상 표시, 추정이면 `추정`을 텍스트로 명시.

핵심: 페이지 증거는 "무슨 일이 있었다"고 보여 주고, 모델 행동은 "이 실행에서 이렇게 움직였다"고 보여 준다. 모델 행동을 페이지 결함처럼 보이게 해서는 안 된다.

## 6. Visual Character

조용한 분석 표다. 원칙은 세 가지: **글자를 키우지 않는다. 정보를 줄이고 정렬을 맞춘다. 강조는 상태 표시와 선택 행 막대 두 가지뿐이다.** 섹션 제목 + 1px 구분선 + 행으로 나눈다.

## 7. Tokens

값은 `src/web/styles.css` 한 곳에만 있고, 컴포넌트는 의미 이름만 쓴다.

글자 (6단계, Tailwind 이름): `text-xs` 11/16 표 머리글·눈금 · `text-sm` 12/16 메타 줄 · `text-base` 13/20 본문·표 셀(기본) · `text-md` 14/20 섹션 제목 · `text-lg` 16/24 대화상자 제목 · `text-xl` 20/28 페이지 제목(화면에 하나). 굵기는 400 / 500(이름·탭·버튼) / 600(제목)만.

간격은 4·8·12·16·24·32. 컨트롤 높이 32(기본) / 28(표·툴바 안), 표 행 40 / 32(행동 목록·묶음 머리 행), 사이드바 216, 선택 막대 3px. 모서리 4px(컨트롤·칩) / 6px(대화상자·메뉴·이미지).

색 (밝게 / 어둡게):

```
canvas        #F6F7F5 / #121413   사이드바, 묶음 머리 행
surface       #FFFFFF / #181B19   본문
raised        #F1F3F0 / #222624   hover, 선택 행, 보조 버튼
ink           #1D211E / #E6E9E6   이름, 값
ink-2         #59615B / #A1A8A3   라벨, 메타
ink-3         #8A918C / #6F7671   `—`, 번호, 단위, 자리표시자만. 문장에는 쓰지 않는다
edge          #DFE3DF / #2F3431   행 구분선
edge-strong   #C5CBC6 / #434A45   입력·버튼 테두리
trace         #2457C5 / #7C9EF0   선택·포커스 전용
primary       ink                 주 버튼은 먹색. 파랑은 쓰지 않는다
```

## 8. Status

상태는 모양 + 색 + 이름이 한 쌍이다(`StatusMark`). 모양만으로도 구분된다. 빈 사각형은 체크박스 전용이라 상태에 쓰지 않는다.

```
해냄         ● 채운 원    reach      #1B7448 / #4CB782
포기함       ◆ 마름모     gave-up    #C2571A / #EC8A4A   주황. 빨강으로 읽히지 않게
잘못 끝냄    ▲ 삼각형     mistaken   #A86A00 / #D9A43A
측정 못 함   ○ 빈 원      unmeasured #8A918C / #7E857F   이유(시간 한도 …)는 옆에 ink-2로
오류로 끝남 (도구)  ×     errored    #59615B / #B5BBB6   도구 쪽 문제라 중립색
```

선택 행은 첫 칸 왼쪽 3px trace 막대 + raised 배경이다. 탭 밑줄은 2px ink다.

모양만 늘어놓은 곳(작업 목록의 최근 실행, 흐름 레일)에는 **범례 한 줄을 항상 화면에 둔다**(`StatusLegend`, 레일 아래 범례). 처음 보는 사람 평가에서 범례 없는 기호는 두 버전 모두 아무도 읽지 못했다(2026-11-03). 상태 모양 옆에는 되도록 이름도 쓴다.

## 9. Typography

본문은 Pretendard, 숫자·ID·명령은 DM Mono. 숫자 열은 오른쪽 정렬 + `tabular-nums`. 기록 원문을 그대로 보여 주려고 합자와 문맥 대체 글자(`->` → `→`)는 끈다.

날짜는 한 형식만 쓴다: `11월 1일 08:21`(올해는 연도 생략). 같은 날의 열은 `08:21`만, 걸린 시간은 `454.8초`처럼 60초를 넘어도 초로 쓴다. 툴팁에 연도·초·시간대를 둔다(`Time`). 값이 없으면 항상 `—`(ink-3)이다.

## 10. Words

용어 하나에 표기 하나: 행동(스텝 아님), 이동, 누르기, 해냄 / 포기함 / 잘못 끝냄 / 측정 못 함 / 오류로 끝남 (도구), 행동 수 (해낸 실행)(비용이라 쓰지 않는다. 돈이나 토큰으로 읽힌다), 막힌 곳, 살펴볼 지점, 관찰된 현상, 목표 단어(구간 수에는 항상 행동 범위 `14–22`를 붙인다), 묶음, 기준 묶음, 실행 프로필, 계획 문서 vN, 깨진 예상, `작업명 #n`.

## 11. Density

표 행 40px, 행동 목록 32px. 설명은 한 줄 이하로 줄이고, 선택지는 라디오 행(라디오 · 이름 · 한 줄 힌트)으로 둔다. 설정은 라벨 200px | 값의 시트 행이다. 기본값에서 바꾼 항목만 보여 주고 나머지는 펼쳐서 본다.

## 12. Core Components

`PageHeader`(경로 · 제목 · `·`로 이은 메타 한 줄 · 동작), `SectionHead`, `StatusMark` / `StatusMarks`, DataTable(shadcn Table, `table-layout: fixed`), GroupRow(표 안의 묶음 머리 행), FilterChip(`라벨 값 ▾`), `FactLine`(사실 한 줄, 0인 지표는 숨김), EvidenceRow(현상 · 어디서 · 실행 수 · 근거 링크), `TraceRail`(계획 줄 + 행동 줄 + 구간 괄호 + 눈금), 시트 / 라디오 행, 대화상자(푸터는 1px 선, 요약 + 버튼), 빈 상태(제목 · 한 줄 · 동작 · CLI 명령), `Time`.

## 13. Screens

| 화면 | 구성 |
|---|---|
| 작업 목록 | 표 하나, 열 폭 고정. 최근 실행은 상태 모양을 늘어놓아 훑어 읽는다. URL은 `www.`를 뺀 호스트+경로. 일괄 동작 툴바는 작업을 골랐을 때만 필터 자리에 나온다. |
| 작업 개요 | 헤더 한 줄 → 사실 한 줄 → 관찰된 현상(근거 링크 `#1 · 행동 9`) → 프로필별 결과 표. 그림 보기는 없다. |
| 실행 상세 | 헤더(시뮬레이션 고지는 메타 줄에 한 번) → 진단 한 번(포기 이유 인용 + 깨진 예상 표, 제목은 `깨진 예상 3 / 전체 8`) → Trace Rail(계획 칸에 시작 행동, 아래에 범례 한 줄) → 행동 목록 \| 선택한 행동 상세(스크린샷) → 계획 문서(접힘). 같은 행동이 이어지면 `다음 항목 ×4`로 묶는다. |
| 실행 기록 | 표 하나에 묶음 머리 행(`묶음` 표시, 체크박스 없음). 실행은 `작업명 #3/5`처럼 그 작업의 전체 실행 수와 함께 쓴다. 시작 열은 시각만. |
| 묶음 | 기준 묶음을 고르면 작업·프로필 / 결과 / 비용 / 막힌 곳 / 살펴볼 지점 / 기준과 달라진 점. 어느 쪽이 나은지는 말하지 않는다. |
| 실행 프로필 | 목록 \| 상세. 네 질문(어떻게 찾나요 / 어떤 AI가 생각하나요 / 어디서 듣나요 / 언제 멈추나요)은 시트 행, 규칙은 바꾼 것만 `이 프로필 · 기본값 · 되돌리기`. |
| 설정 | 상단 탭 AI 연결 / 이 컴퓨터 / 기본 실행 규칙. 연결은 표, 선택지는 라디오 행. |
| 실행 대화상자 | 프로필 체크 목록, 반복 수, 묶음 메모, 푸터에 `실행 6번 · 한 묶음으로 기록`, 버튼 이름에 실행 수. |

## 14. Empty States

illustration을 넣지 않는다. 항상 "무엇이 없는가 / 왜 필요한가 / 다음 행동" 세 가지로 구성한다. (예: 등록된 모델이 없습니다 / 작업을 실행하려면 계획을 세울 모델이 필요합니다. / [모델 연결])

## 15. Error States

모든 오류를 같은 빨간 alert로 처리하지 않는다. 최소 Setup error, Start failure, Runtime failure, Data failure, Connection loss를 구분한다. 각 오류에는 무슨 일이 있었나, 무엇까지 실행됐나, 사용자가 할 수 있는 다음 행동, 원본 오류 보기를 제공한다. Provider의 민감한 원문은 그대로 노출하지 않는다.

## 16. Onboarding

말풍선 튜토리얼을 전체 UI에 순서대로 붙이는 방식은 최소화한다. 개념 설명은 사용 시점에 한다 (처음 `실행 프로필`, `완료 확인`을 만났을 때 한 문장). 말풍선 walkthrough는 보조 수단이다.

## 17. Responsive

Desktop — 실행 상세는 행동 목록 │ 선택한 행동(440px).
Tablet / Mobile — 단순히 column을 아래로 쌓는 것에서 끝내지 않는다. Run Detail에서는 Trace → 현재 행동 → Evidence → Page response → Inspection 순서를 유지하고, 작은 sticky control(`← 이전  17 / 43  다음 →`)을 둘 수 있다.

## 18. Accessibility

Rawstep의 자체 접근성은 제품 신뢰도의 일부다. **Every visualization has a navigable textual equivalent.** Trace rail → 방향키 탐색 + step label, Run strip → 각 실행에 accessible name, 행동 수 chart → 동일 숫자를 text로, 색상 → shape + text 병행.

## 19. Motion Language

motion은 실제 state 변화만 표현한다. 사용: 새 trace step 등장, panel reveal, selection 이동, screenshot transition, connection highlight. 피함: card lift, bounce, confetti, 성공 celebration, decorative gradient animation, constant pulsing. 목표 도달도 축하 이벤트가 아니다.

## 20. Product Voice

판단하지 않으므로 문체도 중립적이어야 한다.

- "문제가 발견되었습니다." 대신 "이 요소에서 포커스가 페이지 밖으로 이동했습니다."
- "모델이 혼란스러워했습니다." 대신 "같은 두 요소 사이를 4번 이동했습니다."
- "접근성이 좋지 않습니다." 대신 "3번의 실행 중 2번에서 목표에 닿지 못했습니다."

## 21. 무엇을 하지 않을 것인가

KPI 카드와 큰 숫자, 카드 속 카드, 왼쪽 색 띠, 점선 박스, 호박색 경고 박스, 알약 칩, ⓘ 아이콘, 같은 진단·고지를 두 번 쓰기. Generic shadcn Dashboard(모든 내용을 `rounded-lg border p-4` 카드로), Testing CI Dashboard(Pass/Fail 숫자가 주인공), AI Assistant(채팅창과 AI 요약 중심), Accessibility Score Tool(페이지에 점수), IDE, Observability Dashboard(metric chart 나열). Rawstep의 핵심 데이터는 경로와 요소다.

## 22. Core Formula

행동의 경로를 trace로, 관찰된 현상을 evidence로, 페이지와 모델의 원인을 source로 분리해 보여 주는 접근성 진단 인터페이스. 차분한 분석 테이블 위에 실행의 흔적을 펼쳐 놓고, 사용자가 한 단계씩 증거를 조사하는 도구.

가장 중요한 기준: **Rawstep이 답을 말해 주는 것처럼 보여서는 안 된다. 사람이 답을 내릴 수 있을 만큼 좋은 증거를 보여 주는 것처럼 보여야 한다.**
