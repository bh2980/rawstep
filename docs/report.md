# Current trace and report outputs

Runs write schema-2.2 `trace.json` plus append-only `trace.jsonl` and deduplicated screenshot blobs under `blobs/<sha256>.png` (events keep `{ sha256, blob, bytes, viewport }` references; `hydrateScreenshots` from `@rawstep/core/trace` restores pixels, and `onEvent`/`MemoryTraceSink` serve embedding); only schema 2.2 is read. A report written next to the trace references the blob files relatively, while `rawstep report` hydrates screenshots so the HTML embeds them wherever `--out` points. Analysis writes a separate `analysis.json`; reports render static, escaped `report.html` and `report.json` with stable evidence references. The old step-table/minimap, prompt logs, cursor images and earlier trace schemas are not the report contract.

`npx rawstep report <run-dir>` works without an analyzer. The HTML report begins with the recorded outcome, reason and execution stage, followed by the first recorded execution failure or interruption, privacy/evidence counts, action results, and independent verifier results. Each verification rule links to its saved evidence and shows the observed grounds. An unmet check during a successful run is shown as “Not satisfied” at that step, not as a failed run. Older traces without per-rule evidence remain readable and explicitly show that the grounds were not recorded.

Raw events are collapsed individually and retain their stable anchor IDs. All trace and analyzer text is HTML-escaped; a restrictive Content Security Policy disables scripts and remote resources. Keyboard screenshots are embedded as explicit visual evidence. Privacy counts distinguish retained keyboard screenshots, screenshots omitted after input, diagnostic screenshot references, redacted speech, and redacted verifier evidence. Diagnostic image references do not prove that the external files still exist, and retained pixels are not anonymized.

The additive `report.json.summary` projection contains `modality`, `modalities`, `counts`, `actions`, `firstFailure`, and `verification`. Action execution success does not imply task completion; the run outcome is authoritative. Reports and analyzers never rewrite the original trace or change its outcome.

`mock-run` reports display a prominent simulated VoiceOver warning. `modality: "simulation"` identifies a pure simulated run; mixed traces list every observed modality. `readableSimulationOutputEvents` and `redactedSimulationOutputEvents` are separate from native `readableSpeechEvents` / `redactedSpeechEvents` and screenshot counts. Observation aggregates and transport acknowledgments are not counted as output. An empty simulation startup trace remains labeled using environment provenance. Built-in analysis never emits a missing-native-speech warning solely because a simulation produced no native output, and simulated results cannot establish native VoiceOver behavior or conformance.

See the [current README](../README.md) and the [source map](./editing-map.md). Historical workspace-specific instructions were removed with their implementation.

## Trace privacy

Task input values and their URL/form-encoded forms are redacted from persisted payloads before analyzers can read them. Whole-value matching alone cannot remove characters spoken individually. After text entry starts, the runner therefore conservatively redacts subsequent protocol payloads, speech observations, related diagnostic content, and outcome details and suppresses later diagnostic screenshots. This privacy boundary stays active through cleanup because delayed echoes can arrive after an acknowledgement. Redaction never rewrites a screenshot reference. Policies refer to inputs by name and never receive their values (see [Hiding input values from the policy](./task.md#hiding-input-values-from-the-policy)).

This is a deliberate evidence/privacy tradeoff: an input-heavy trace may lose much of its later raw speech. It does not claim comprehensive anonymization of arbitrary page content or screenshots captured before input. Review artifacts before sharing them. Programmatic `runTask` callers may explicitly set `includeSensitiveInputValues: true` to retain sensitive evidence; it exposes values in saved artifacts and to custom analyzers. The CLI provides no opt-out flag.
