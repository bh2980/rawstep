# 오케스트레이션과 실험 조건 개편

2026-10-07부터의 논의와 결정을 모은 개발 기준 문서다. 이 개편 작업은 이 문서를 기준으로 진행하고, 결정이 바뀌거나 작업이 끝나면 이 문서를 먼저 고친다. 진행 상황은 8장에서 관리한다.

시안: https://claude.ai/artifact/Y4CxuFm4DZPDS6efNCPSdd (작업 상세 / 실험 조건 / 실행 상세)

## 1. 배경

- Rawstep의 목적은 모델이 사람처럼 성공하는 것이 아니다. 페이지가 어디서 사람을 힘들게 하는지 **마찰 신호**를 얻는 것이다. 모델이 헤맨 지점, 다시 생각해야 했던 지점이 그 신호다.
- 모델이 직접 이동을 결정해야 한다. 그래야 "경로가 너무 길다", "길을 잃는다" 같은 신호가 나온다. 모델 없는 측정(목표까지 최소 단계 등)은 모델이 얼마나 헤맸는지 재는 **기준선**으로 쓴다.
- **Jev 같은 decision 모델**: 빠르고 싸고 후보 중 하나를 고르는 데 능하다. 대신 계획하지 못하고 판단력이 약하다. **LLM**: 계획하고 상황을 해석하지만 느리고 비싸다.
- Jev 단독은 일반 쇼핑몰에서 성공한 적이 없다. LLM 단독은 너무 느리고 성공률도 낮았다. 공통 원인은 둘이었다.
  - **작업이 너무 길다.** 단계마다 맞게 고를 확률이 97%여도 150단계면 끝까지 성공할 확률은 1% 수준이다.
  - **모델이 행동 결과를 몰랐다.** 실패한 행동을 알지 못해 같은 실패를 반복했다. → 해결함(8장)
- 그래서 **LLM이 계획하고 Jev가 실행하는 오케스트레이션**을 도입한다. 실행 모델은 판단력이 약하므로, 계획 문서가 그 부족한 부분을 채워야 한다. Kiro나 Spec Kit처럼 큰 계획 안의 세부 작업, 작업별 상태와 완료 조건, 현재 위치, 변경 이력, 작업별 수행 기록이 제대로 관리되어야 오케스트레이션 계층이 의미가 있다.
- 단위는 처음에는 **한 페이지 작업**으로 잡는다. 예: 상품 페이지에서 장바구니 담기.

## 2. 진단

**가장 큰 문제: 첫 오케스트레이션 구현(`f4a1f5a`)은 계획을 관리하지 않는다.** "계획 → 작은 목표 하나씩 → 막히면 통째로 새 계획"의 최소 반복 구조뿐이다.

| 항목 | 첫 구현 |
|---|---|
| 계획의 계층 | 대략 경로(문장)와 작은 목표 목록이 따로 있고 연결되지 않음 |
| 진행 상태·현재 위치 | 상태 데이터가 없음. 모델 호출 기록의 목표 문장에서 추측해야 함 |
| 계획 변경 | 통째로 교체. 버전, 바뀐 이유, 버려진 작업이 남지 않음 |
| 행동과 작업의 연결 | 어떤 행동이 어떤 작업을 위한 것인지 연결되지 않음 |
| 계획 모델 입력 | 처음엔 목표와 발화 한 줄뿐. 허용 행동이 없음. 다시 계획할 때도 작업별 시도 내역과 도움 요청 이유가 없음 |
| 실행 모델 입력 | 계획 흐름(지금 어디쯤인지)과 현재 작업의 시도 내역이 없음 |
| 완료 판단 | 실행 모델의 "완료"를 그대로 믿음 |
| 화면 | 단계 상세 안의 "PLAN" 메모뿐. 한 단계 안의 여러 모델 호출 중 마지막만 남음 |

그 밖에 코어·대시보드 전수 조사(2026-10-07)에서 찾은 문제:

| 문제 | 위치 |
|---|---|
| "에이전트"는 실행 프로필 이름만 바꾼 것이다(`6c19360`). 모델, 허용 행동, 멈춤 조건이 한 덩어리 | config.ts `agentSchema` |
| `policy` 하나에 실행 모델 동작, 사용자 조건, 멈춤 규칙, 재계획 한도가 섞여 있고, 작업이 아무 값이나 덮어씀 | config.ts `policySchema`, `taskSchema` |
| 허용 행동을 이름 붙여 저장·관리하는 화면이 없음 | PermissionPresets |
| "이 컴퓨터"에 실험 조건(스크린리더 백엔드), 이 컴퓨터 설정(경로·주소), 공유 프로젝트 설정(사후 분석)이 섞여 있음 | MachinePage |
| 멈춘 이유가 잘못 기록됨. 재계획 한도는 "반복 감시"로, 계획 모델의 완료 판단은 실행 모델의 판단으로 남음 | orchestration.ts, 진단·단계 라벨·힌트 |
| 모델이 쓰이는 역할이 흩어져 한곳에서 보이지 않음(실행, 계획, 해설, 제안, 포커스 판단, 멈춘 이유 진단) | 여러 곳 |
| 비밀값 입력 뒤 계획 기록이 통째로 가려짐 | runner/index.ts |
| 다시 계획한 뒤에도 반복 감시 기준이 초기화되지 않아, 새 계획을 따르기 전에 멈출 수 있음 | orchestration.ts |
| 실행 기록에 어떤 조건·모델로 돌렸는지 없음 | runner `run.started` |
| 망설임 힌트가 계획용 선택지까지 점수에 넣음 | hints/index.ts |
| 실행 상자가 키보드 모드로 시작해, 스크린리더 전용 조합이면 처음부터 실행 불가로 뜸 | RunControl 외 2곳 |
| 작업의 정책 덮어쓰기가 편집 불가한 재계획 한도까지 복사해 고정함 | TaskSettings |
| 버그: 포커스 판단(키보드 기능)이 스크린리더 실행까지 막음 | plan.ts |
| 버그: 결과에 영향 없는 사후 분석 모델의 키가 없으면 실행이 막힘 | plan.ts, run.ts |

## 3. 오케스트레이션 설계

### 3.1 역할

| 역할 | 모델 | 하는 일 |
|---|---|---|
| 계획 모델 | LLM만 (글을 써야 하므로) | 계획 문서 초안을 쓰고 고친다. 고칠 때는 변경 이유를 적는다 |
| 실행 모델 | decision 모델 또는 LLM | 현재 작업 하나 안에서 행동을 고른다. "작업 완료"나 "도움 요청(이유)"을 고를 수 있다 |
| Rawstep | 코드 | 계획 문서를 소유한다. 작업 id·상태·현재 작업·행동 수·버전·이력을 관리하고, 완료 주장을 확인하고, 다시 계획할 때를 정한다 |
| 해설 모델 | LLM (선택) | 실행이 끝난 뒤 해설. 결과에 영향 없음 |

### 3.2 참고한 구조: Kiro, Spec Kit

| Kiro / Spec Kit | Rawstep 계획 문서 |
|---|---|
| 요구사항·명세: 사용자 이야기와 인수 조건(Kiro), 무엇을·왜·성공 기준(Spec Kit) | **성공 기준**: 목표를 사용자가 들을 수 있는 조건으로 쓴 목록(C1, C2…). 예: "C2: 담기를 누른 뒤 '장바구니에 담김' 같은 안내가 들린다". 작업 파일의 완료 확인(검증기)과 별개로, 계획 모델이 사람 입장에서 씀 |
| 설계·계획: 접근 방식과 기술 결정 | **전략과 가정**: 접근 방식 한 줄과 관례에서 나온 가정 목록(A1, A2…). 예: "A1: 상품 페이지에 '장바구니 담기' 버튼이 있다". 가정은 실행하면서 "맞음 / 틀림"이 정해진다 |
| 작업 목록: 번호(1.1, T001), 단계 묶음, 체크박스, 요구사항 참조 | **단계와 작업**: 단계별 번호(1, 1.1, 1.2), 상태, 완료 조건, **어떤 성공 기준을 위한 작업인지**(C 참조), **어떤 가정에 기대는지**(A 참조) |
| 진행 상태 실시간 표시 | 현재 작업, 작업별 행동 수, 완료 확인 결과 |
| 단계 끝 체크포인트(Spec Kit), 수렴 점검(converge) | **단계 체크포인트**: 단계의 작업이 다 끝나면 계획 모델이 그 단계가 맡은 성공 기준이 충족됐는지 점검하고 다음 단계로 간다. **마지막 점검**: 모든 기준을 점검한 뒤 완료를 선언하고, 독립 검증기가 최종 판정 |
| 명세가 바뀌면 문서 갱신 | **다시 계획 = 문서 수정**. 어떤 가정이 틀렸는지, 무엇을 바꿨는지를 이력에 남긴다 |

이렇게 하면 계획을 바꿀 때 "무엇이 예상과 달랐나"가 가정 단위로 남는다. 예: "A1 틀림: 담기 버튼이 폼 컨트롤 순서에 없음". 이것은 그대로 페이지 마찰 신호의 후보가 된다. 사람이 읽을 수 있게 `plan.md`(체크박스 형식)로도 내보낸다.

### 3.3 계획 문서

실행마다 하나. `packages/policies/src/policy/plan-document.ts`.

```
목표: Thor Hammer를 장바구니에 담기                                   v2
성공 기준
  C1 상품 이름 "Thor Hammer"가 들린다                                ✓ 충족
  C2 담은 뒤 담겼다는 안내가 들린다                                   ○
전략: 상품 페이지에서 담기 버튼을 찾아 누른다
가정
  A1 담기 버튼은 수량 칸 다음에 있다                                  ✕ 틀림 (v2)
  A2 담기 뒤 안내가 읽힌다                                            ? 미확인
1. 상품 확인                                         체크포인트 ✓ (C1)
   [x] 1.1 상품 제목 듣기            C1      행동 3 · 완료 확인: 들림
2. 장바구니에 담기
   [-] 2.1 담기 버튼 찾기            A1      포기 (v1) · 행동 9 · 도움 요청: 완료 단서를 찾을 수 없음
   [~] 2.2 폼 컨트롤 이동으로 버튼 찾기 (v2)  진행 중 · 행동 4/12 · 완료 조건: "Add to cart, button"
   [ ] 2.3 누르기                    C2, A2
3. 결과 확인
   [ ] 3.1 담겼는지 확인             C2
변경 이력: v1 → v2 (행동 12 전, 계기: 도움 요청/no-cue)
  틀린 가정: A1 · 이유: "수량 칸 다음에 담기 버튼이 들릴 줄 알았지만 9번 이동해도 들리지 않았다"
```

- 성공 기준: `C1…`, 사용자가 들을 수 있는 조건, 상태(미확인 / 충족 / 미충족).
- 전략과 가정: 전략 한 줄, 가정 `A1…`과 상태(미확인 / 맞음 / 틀림).
- 작업: 내부 `id`와 표시 번호(1.1), 목표, 완료 조건(정확한 문구는 따옴표로), 맡은 성공 기준, 기대는 가정, 상태(대기 / 진행 중 / 완료 / 포기 / 실패), 행동 수, 추가된 버전, 끝난 방식(완료·교체·한도, 행동 번호, 완료 확인 결과).
- 단계: 제목, 맡은 성공 기준, 체크포인트 결과.
- 현재 작업은 문서가 명시적으로 가리킨다(`current`). 앞에서부터 첫 번째 열린 작업이 현재 작업이 된다.
- **다시 계획 = 문서 수정.** 계획 모델은 유지할 작업을 `keep: id`로 가리키고 새 작업을 추가한다. 끝난 작업은 상태 그대로 유지된다. 빠진 열린 작업은 "포기"로 닫히고, 원래 단계 이름과 함께 `retired`에 남는다. 버전이 오르고, 계기·도움 이유·계획 모델의 변경 이유·추가/포기된 작업이 이력에 남는다.
- **완료 확인**: 실행 모델이 "작업 완료"를 고르면, Rawstep이 완료 조건의 따옴표 문구가 지금 발화나 직전 발화에 있었는지 대조한다. 결과는 `heard` / `not-heard` / `unchecked`(따옴표 없음)이다. 작업은 완료로 넘기되 결과를 기록하고, 다음 계획 때 계획 모델이 볼 수 있게 한다.

### 3.4 흐름

1. **시작**: 계획 모델이 성공 기준, 전략과 가정, 단계와 작업을 쓴다(v1). 첫 작업이 현재 작업이 된다.
2. **매 단계**
   - 반복 감시를 확인한다. 기준은 현재 계획 버전 이후의 기록이다.
   - 다시 계획할 계기가 있는지 확인한다: 현재 작업에서 행동 실패가 `failureLimit`회 연속, 변화 없음이 `noChangeLimit`회 연속, 행동 수가 `stepActionLimit` 도달.
   - 실행 모델에게 묻는다.
3. **실행 모델의 답**
   - 행동 → 실행기로 돌려준다. 그 행동은 현재 작업과 계획 버전에 기록된다.
   - 작업 완료 → 완료 확인 → 다음 작업. 같은 실행기 단계 안에서 다시 묻는다.
   - 도움 요청(이유) → 다시 계획.
   - 단계의 작업이 모두 끝나면 **체크포인트**: 계획 모델이 그 단계가 맡은 성공 기준과 관련 가정을 점검해 상태를 정하고, 필요하면 남은 계획을 고친다(계기: `checkpoint`).
   - 열린 작업이 없으면 계획 모델에게 마지막 점검을 맡긴다(계기: `plan-finished`). 모든 기준이 충족됐다고 판단하면 완료, 아니면 작업을 더한다.
4. **계획 모델이 `complete`라고 하면** 멈추고 독립 검증기가 판정한다. 멈춘 이유는 `planner`로 기록한다.
5. **`maxReplans`를 넘으면** 현재 작업을 "실패"로 닫고 멈춘다. 멈춘 이유는 `orchestration-limit`로 기록한다.
6. 한 실행기 단계 안의 모델 호출은 최대 8번이다(완료·다음 작업이 반복되는 경우를 막음).

### 3.5 모델이 받는 정보

**계획 모델**
- 목표
- 계기와 도움 요청 이유
- 현재 발화
- 실행 모델이 실제로 쓸 수 있는 행동과 입력 이름. 비밀값은 이름만.
- 계획 문서 전체: 상태, 완료 확인 결과, 이력 포함
- 작업별 시도 내역: 행동, 실행 결과와 실패 이유 코드, 변화 여부, 행동 전 발화
- 출력: `{ complete, rationale, criteria: [{ keep?, text, status }], strategy, assumptions: [{ keep?, text, status }], phases: [{ title, criteria: [C 참조], tasks: [{ keep?, goal, done, serves: [C], relies: [A] }] }] }`
- 사람이 들을 수 있는 정보만 준다. 접근성 트리 전체는 주지 않는다. 그래야 "어디서 막히나" 신호가 유지된다.
- 계획 지침(사용자 작성)은 Rawstep 기본 규칙 뒤에 덧붙인다. 페이지를 아는 사람만 아는 정보는 쓰면 안 된다.

**실행 모델**
- 목표
- 계획 요약: 작업마다 단계 이름, 목표, 상태. 지금 어디쯤인지 알게 하는 용도
- 현재 작업과 완료 조건, 다음 작업
- 이 작업을 시작한 뒤의 시도 내역
- 현재 발화와 최근 기록
- 선택지: 허용 행동, 작업 완료, 도움 요청 3종(완료 단서를 찾을 수 없음 `no-cue` / 행동이 먹히지 않음 `no-effect` / 이미 이뤄진 것 같음 `already-done`)

### 3.6 기록

- 정책 증거(trace의 `policy.evidence`), 모두 `role` 포함
  - `orchestration-plan`(role planner): 버전, 계기, 도움 이유, 적용 후 계획 문서 전체, 이번 변경 이력, 모델, 지침 지문(id·version·sha256), 걸린 시간
  - `orchestration-task`: 작업 id, 버전, 이전·이후 상태, 끝난 방식, 행동 수
  - `model-inference`(role executor): 작업 id, 계획 버전, 후보, 고른 것, 점수
  - `orchestration-limit`
- 모든 행동에 계획 버전과 작업 id를 붙인다.
- `plan.json`과 `plan.md`(체크박스 형식, 사람이 읽기용): 실행 폴더에 최종 계획 문서를 저장한다. 실행 중에는 대시보드가 trace 증거로 실시간 계획 문서를 재구성한다.
- 비밀값 입력 뒤에도 구조(버전, 상태, 작업 id, 횟수, 이유 코드, 고른 후보 id)는 남기고, 계획 문구와 발화만 가린다.
- 멈춘 이유: `model`(실행 모델), `planner`(계획 모델의 완료 판단), `exploration-guard`(반복 감시), `orchestration-limit`(재계획 한도).

### 3.7 신호

- 다시 계획한 지점, 도움 요청(이유별), 포기한 작업, 완료 확인 실패(`not-heard`), **틀린 가정**, **미충족 성공 기준**은 마찰 신호다. 힌트 종류: `replan`, `help-request`, `task-limit`, `unverified-done`. 출처는 "실행"이고 원인은 단정하지 않는다. 페이지가 어려웠을 수도, 계획이 틀렸을 수도 있다.
- 망설임 힌트는 계획용 선택지(작업 완료, 도움 요청)를 제외하고 계산한다.

## 4. 실험 조건

실험 = **작업 × 모델 조합 × 행동 조합 × 페이지 환경 × 보조기술 환경 × 모드**

| 조건 | 담는 것 | 실험 조건인가 |
|---|---|---|
| **모델 조합** | 구조(단독 / 계획 + 실행), 계획 모델과 지침, 모드별 실행 모델과 지침·동작(기록 길이, 포커스 판단), 해설 모델(선택. 비우면 프로젝트 기본값) | 계획·실행: 예. 해설: 아니오(기록만 하고 비교 기준에서 뺌) |
| **행동 조합** | 모드별 허용 키·스크린리더 동작·입력값 사용. 예: 초보(다음/이전/누르기), 숙련(제목·폼 이동·검색) | 예 |
| **페이지 환경** | 화면 크기, 텍스트 배율·간격, 색상·대비, 움직임 줄이기, OS 확대·고대비 요구 | 예 |
| **보조기술 환경** | 시뮬레이션 / VoiceOver / NVDA | 예. 모의 VoiceOver와 실제 VoiceOver 비교가 가능해짐 |
| **실행 규칙** | 반복 감시, 같은 화면·변화 없음 한도, 모델 중도 포기 허용, 재계획 한도, 작업 최대 행동 수, 실패·변화 없음 재계획 기준. 프로젝트 기본값 + 프리셋 + 작업별 덮어쓰기 | 예 |
| **실행 프리셋** | 위 다섯 조건 묶음 | — |
| **프로젝트 설정** | 기본 해설 모델·지침, 완료 확인 제안 모델 | 아니오 |
| **이 컴퓨터** | 보조기술별 AT Driver 주소, 브라우저 경로, 화면 표시 여부, 봇 확인 대기 | 아니오 |

**원칙**

- **등록은 선택, 만들기는 어디서든.** 작업 상세의 각 조건 칸에서 불러오기 / 그 자리에서 고치기(작업 전용 사본) / 새로 만들기를 할 수 있다. "공용으로 저장"과 "프리셋으로 저장"은 사용자가 원할 때만 한다. 시스템이 먼저 권하지 않는다.
- 공용 항목을 고치면 사본이 생기고 공용 항목은 그대로 둔다. 조용히 덮어쓰지 않는다.
- 결과를 바꾸는 설정은 모두 실험 조건이다. 실행 기록에 **내용 전체**와 원본 참조를 남긴다. 비교는 이름이 아니라 내용으로 판단한다.
- 해설 모델이 없거나 키가 없어도 실행은 막지 않는다. 해설만 건너뛴다.
- 조건의 기본값 우선순위: 작업의 지정 > 작업의 프리셋 > 첫 번째 공용 항목.
- 용어: 위 다섯 가지는 어디서나 "실험 조건"이라고 부른다. 역할 이름은 "계획 모델 / 실행 모델 / 해설 모델"로 통일한다.

## 10. 열린 문제

- **실행 모델의 선택 편향**: Jev는 목표·작업 문구와 비슷한 글자가 든 선택지(완료 주장, 로고 링크 누르기)를 고르는 경향이 있다(11장). 완료 선택지 문구에서 완료 조건을 빼거나, 계획 모델이 고른 행동 후보만 보여 주는 방식을 검토한다.
- **시작 페이지 판단**: 사이트가 모든 페이지에 같은 제목을 쓰면(Demoblaze "STORE") 계획 모델이 시작 페이지를 오해한다. 목표 문장에 시작 페이지를 적게 하고 규칙에 "목표가 말한 페이지에서 시작"을 넣었다.
- **계획 모델 호출 실패**: Gemini 3.1 Pro 미리보기 모델이 짧은 간격의 4번째 호출에서 실패했다(원인 기록 안 됨, 호출 한도 추정). 실패 종류(한도·형식·연결)를 기록하고 한도면 기다렸다 한 번 다시 시도할지 정한다.

- **키보드 모드**: 계획 모델 입력(스크린샷), 실행 모델(이미지), 포커스 판단과의 관계를 7단계에서 설계한다.
- **보조기술 환경의 작업 전용 사본**: 보조기술 환경은 `owner`가 없어 작업 전용 사본을 만들 수 없다. 백엔드 종류 하나뿐이라 지금은 필요 없다고 보고 둔다.
- **기본 행동 조합 3개**: 5장은 초보·숙련·위젯 탐색 세 개를 기본으로 두지만, 지금 `defaultConfig()`는 `Basic` 하나만 만든다. 실제 실행 검증 뒤 숙련·위젯 탐색 구성을 정해 추가한다.
- **멈춘 이유 진단은 키보드 전용**: `--diagnose-stop`은 마지막 스크린샷을 쓰므로 키보드 모드에서만 된다(`diagnose-keyboard-only`).
- **프리셋을 고르면 개별 조건 선택이 지워짐**: 작업 실행 상자에서 프리셋을 바꾸면 그 작업에서 따로 고른 조건 id가 지워진다. 의도한 동작(프리셋 = 묶음 적용)이지만, 사용해 보고 불편하면 '프리셋 위에 덮어쓰기 유지'로 바꾼다.

## 11. 실제 실행 검증 기록

2026-10-07, 시뮬레이션 VoiceOver, 행동 조합 Basic(다음·이전·누르기), 각 1회.

| 작업 | Jev 단독 | 계획(Gemini 3.1 Pro) + Jev |
|---|---|---|
| CityLights 홈 → 설문 페이지(긴 작업, 40행동) | 40행동 한도, 목표 못 감 | 22행동째 Survey 링크 도달, 이후 실행 모델의 거짓 완료 주장으로 계획이 틀어져 재계획 한도로 멈춤(25행동) |
| Toolshop Pliers 상품 페이지에서 장바구니 담기(한 페이지, 25행동) | 상단 배너·메뉴만 돌다 25행동 한도 | 1차: 계획 모델이 홈이라고 착각(페이지 제목 없음), 완료 조건을 확인 불가능한 문장으로 씀 → 11행동에서 재계획 한도. 2차(아래 수정 후): 페이지 제목으로 상품 페이지임을 알고 `cue "Add to cart"`로 계획했지만 5행동째 계획 모델 호출 실패 |

발견하고 고친 것:
- 실행 모델이 작업을 하지 않고 "완료"를 고른다 → **완료 문구(`cue`)가 들리지 않으면 완료 주장을 받아들이지 않는다.** 그 단계에서는 완료 선택지를 빼고 다시 고르게 하며, `orchestration-claim` 증거와 `unverified-done` 힌트(관찰됨)를 남긴다.
- 계획 모델이 완료 조건을 "I have found it"처럼 확인할 수 없게 쓴다 → **작업마다 `cue`(들려야 할 정확한 문구)를 필수로 받는다.**
- 계획 모델이 지금 어느 페이지인지 모른다 → **관찰에 페이지 제목(`title`)을 넣고 계획 모델에 준다.** 비밀 입력 뒤에는 기록에서 가린다.
- 새 계획을 받자마자 행동 없이 도움을 요청한다 → **"문구를 못 찾음"·"효과 없음" 도움 요청은 그 작업에서 한 번 이상 행동한 뒤에만 고를 수 있다.** "이미 끝난 것 같음"은 언제나 가능.

### 2차: Codex CLI 계획 모델 (2026-10-07)

계획 모델을 Codex CLI(ChatGPT 로그인, gpt-5.5, 추론 보통)로 바꿔 API 비용 없이 반복했다. 계획 호출 1번에 약 10~15초.

- Toolshop 상품 ID는 데모 데이터 초기화 때 바뀐다. 이전 Toolshop 실행은 상품이 404인 빈 페이지였다. 안정적인 한 페이지 작업으로 Demoblaze "Samsung galaxy s6 상품 페이지에서 장바구니 담기"(성공: `addtocart` POST 200)를 쓴다.
- 고친 것:
  - 계획이 같은 작업을 유지하면 행동 한도가 바로 다시 걸리던 버그 → 한도는 작업이 (다시) 시작된 뒤의 행동만 센다. 실행 모델에도 그 수를 준다.
  - 실행 모델이 행동 없이 "이미 끝남" 도움 요청을 반복 → 도움 요청은 작업에서 3번 행동한 뒤부터, 거절된 완료 주장 직후에는 "이미 끝남"을 빼고 묻는다.
  - 실행 모델이 "성공"으로 실행을 끝냄 → 계획 구조에서 실행 모델은 행동만 고른다. 끝냈는지는 계획 모델과 실행 확인이 정한다.

## 12. 실험 설계 (2026-10-13 논의, 진행 중)

검증 실행을 바로 늘리지 않고, 무엇을 묻는지부터 정한 뒤 그 질문에 답할 수 있게 하네스를 바꾼다. 하네스 변경이 필요하면 바꾼다.

### 12.1 과거 기록에서 확인한 것

10월 6~7일 오케스트레이션 실행(원본 프로젝트 `.rawstep`)에서 실행 모델(Jev)의 선택 중 "완료"·"도움 요청"이 42~100%였다(Demoblaze 6/6, 16/38, 10/23, Toolshop 5/9). 완료 선택지 문구가 `Current task done: link, Samsung galaxy …`처럼 작업 목표 단어를 담고 있어, Jev가 이동 대신 글자가 비슷한 메타 선택지를 골랐다. 이때 최고 확률 중앙값은 0.36~0.57로, Jev 단독 실행(0.67~0.78)보다 낮았다. Jev 단독 실행은 메타 선택은 거의 없지만 행동 한도(25~40)에 걸렸다. Jev 단독은 더 돌리지 않고 이 기록을 기준선으로 쓴다.

### 12.2 판단 기준

rawstep의 목적은 모델의 성공이 아니라 마찰 신호다. 요소마다 이렇게 묻는다: **이 요소가 실제 사용자에 더 가까워지게 하나, 모델을 성공하게만 하나?** 실제 사용자가 모를 정보(DOM에서 뽑은 이 페이지의 구조 등)는 성공률을 올려도 찾아야 할 마찰을 가리므로 주지 않는다. 일반 웹 관례처럼 실제 사용자도 아는 것은 성능 향상이 아니라 사용자 숙련도 조건으로 다룬다.

- B. 계획: 모델과 추론 강도, 계획에 쓰는 정보(들린 발화 / 페이지 제목 / 로터 개요, 로터는 단계 비용 포함), 계획 시점(처음 / 단계마다 확인 / 막혔을 때), 가정을 사실로 다루지 않는지
- C. 작업 쪼개기: 크기(L1 하위 목표 "상품 정보 영역으로" / L2 목표 요소 "'Add to cart' 버튼까지" / L3 방법 지정 "제목 단위로 'Add to cart'가 들릴 때까지"), 작업당 행동 한도, 실패 시 재시도와 재계획
- D. 실행 모델에게 주는 것: 작업 형식(자연어 / 구조화된 목표 {역할, 이름, 들려야 할 문구} / 들려야 할 발화), 정보량(현재 작업만 / 계획 개요 / 다음 작업 / 기록 길이), 언어(영어 고정), 행동 결과 피드백(효과·포커스 변화)
- E. 실행 모델의 선택지: 행동 종류, 문구(행동만 / 행동과 대상 "누르기: 링크 'Home'"), 작업별로 좁히기
- F. 판단 권한: 작업 완료(Jev 주장 / rawstep `cue` 확인), 계획 모델 호출(Jev 도움 요청 / rawstep 신호 / Jev 확신도), 실행 종료 주체. 12.1로 보아 rawstep이 판정하는 쪽을 기본으로 둔다.

**측정 (H)**: 목표 도달, 최소 경로 대비 단계 수, 반복·되돌아감, 재계획 수, 넘김 이유, 거절된 완료 주장, 실패 원인(시뮬레이터 / 계획 / 실행 / 페이지), 비용과 시간

### 12.4 원칙

- 한 번에 한 변수만 바꾼다. C~E는 계획 모델을 빼고 사람이 쓴 계획으로 고정해 실행 모델 쪽 효과만 본다.
- 실행 모델 판단만 보는 질문은 기록된 상태를 다시 넣는 오프라인 평가로 싸게 비교한다.
- 최소 경로를 아는 로컬 fixture 5~8개를 주로 쓰고, 실제 사이트는 확인용으로 쓴다.
- 조건마다 3~5회 반복한다.
- 남은 핵심 질문은 C와 D다.

### 12.7 실행 모델 선택지 문구 (2026-10-13, 오프라인 평가)

확인 실행(장바구니, 조건 4개 × 1회)에서 두 문제가 보였다: 선택지가 `Screen reader intent: activate`일 때 Jev는 버튼 위에서도 누르지 않고 지나쳤고, 누르기 문구에 지금 항목 이름을 넣자(`Activate the current item ("link, Cart (0)")`) 목표 단어가 겹치는 링크(Phones, Cart)를 눌렀다. 페이지 3개를 시뮬레이터로 걸어 만든 상태(대상 위 4개, 목표 단어 링크 10개, 그 밖 14개)로 Jev에 다시 물었다.

| 변형 (작업 맥락) | 대상 위에서 누름 | 목표 단어 링크에서 누름 | 그 밖에서 누름 |
|---|---|---|---|
| A 내부 이름 `Screen reader intent: activate` | 33% | 0% | 14% |
| B 풀어 쓴 문구 + 상태 `currentItem` | 100% | 30% | 21% |
| B2 B에서 `currentItem` 뺌 | 25% | 0% | 7% |
| C 누르기 문구에 항목 이름 | 100% | 50% | 29% |
| D 누르기 결과를 설명하는 문구 + `currentItem` | 100% | 30% | 21% |
| E B + 이동 작업에서는 누르기를 뺌 | 100% | 0% | 0% |

결정: 선택지 문구는 풀어 쓰고, 지금 항목은 문구가 아니라 상태 `currentItem`으로 준다(누르게 만드는 것은 문구가 아니라 위치 정보다). 계획의 작업에 `activates`(누르기로 끝나는 작업인지)를 두고, rawstep이 판단할 때 이동 작업에서는 누르기를 뺀다. 계획이 없는 단독 실행에서는 잘못 누르기가 30~46%로 남는다. 계획이 이동과 누르기를 나눠 주는 것 자체가 오케스트레이션의 효과다. 대상 상태가 4개뿐이라 강한 신호로만 본다.

`currentItem`과 라이브러리 목적 (2026-10-13 논의):
- DOM이 아니라 이미 들린 발화의 마지막 줄이다(`currentItem()` in policies/policy/speech.ts). 새 정보가 아니라 `speech`·기록에 있던 문장에 "지금 커서 위치"라는 이름표를 붙인 것이고, 실제 사용자도 방금 들은 항목이 자기 위치임을 안다. 시뮬레이터와 실제 VoiceOver(AT Driver)에서 같은 방식으로 나온다.
- Rawstep은 접근성이 나쁜 페이지를 많이 다룬다. 그런 페이지에서는 `currentItem`도 그만큼 나쁘다(이름 없는 버튼은 "button"만, 엉뚱한 알림은 엉뚱한 위치). 보정하지 않는다: 그 나쁨이 마찰로 드러나야 한다.
- 알려진 약점: 마지막 발화가 늘 커서 위치는 아니다. 누른 뒤 상태 영역 알림("Product added to cart")이 `currentItem`이 되면 실제 사용자와 달리 알림과 위치를 구분하지 못한다. 실험 결과에서 이 경우를 따로 본다. 문제가 되면 발화 종류(커서 항목 / 페이지 제목 / 알림)를 구분해 커서 항목만 쓴다. 시뮬레이터는 발화마다 종류를 이미 기록한다.

Jev(결정 모델)를 실행 모델로 쓸 때의 원칙 (지금까지의 근거):
1. 메타 선택지(완료 주장, 도움 요청, 포기)를 주지 않는다. 작업 목표 단어를 담은 메타 선택지를 42~100% 골랐다(12.1).
2. 선택지 문구는 풀어 쓰되 페이지 문구를 넣지 않는다. 목표 단어와 겹치는 문구에 끌린다(12.7 C).
3. 지금 위치는 상태(`currentItem`)로 준다. 없으면 대상 위에서도 누르지 않는다(12.7 B2).
4. 할 수 없는 행동은 선택지에서 뺀다. 이동 작업에서 누르기를 빼자 잘못 누르기가 사라졌다(12.7 E).
5. 시키지 않은 탐색 방법은 쓰지 않는다. 확인 실행에서 "제목 단위로"라고 적힌 L3만 제목 이동을 썼다(2단계 실험에서 확인 중).

### 12.8 2단계 실험 C: 작업 크기 (2026-10-13)

조건: 시뮬레이션 VoiceOver, 행동 조합 "이동 + 제목 이동"(다음·이전·누르기·다음 제목·이전 제목), 실행 모델 Jev `jev-1.13.0`, rawstep 작업 판단(12.7 반영: `currentItem`, 이동 작업에서 누르기 제외), 작업당 행동 한도 20, 실행당 40, 계획은 고정 파일(examples/orchestration/plans). 작업 3개 × 조합 4개 × 3회 = 36회. 결과 폴더: examples/orchestration/.rawstep/experiments-cli/2026-10-12T23-22-38-321Z (git 제외).

| 작업 (최소 행동) | Jev 단독 | L1 하위 목표 | L2 목표 요소 | L3 방법 지정 |
|---|---|---|---|---|
| 장바구니 (5) | 0/3 (반복 감시로 멈춤, 31~37행동) | 0/3 | 0/3 (이동 작업 한도 초과) | **3/3, 5행동 (최소)** |
| 반품 기한 (6) | 0/3 | 0/3 (2행동 만에 포기) | **3/3, 19행동** | **3/3, 6행동 (최소)** |
| 알림 설정 (10) | 0/3 | 0/2 (+오류 1) | **3/3, 19행동** | **3/3, 16~17행동** |

- 처음 36회 중 5건(14%)이 Jev 결정 API 호출 실패("Decision call failed")로 끝났다. 모델 판단이 아니라 연결 문제라 분모에서 빼고, 한 번씩 다시 돌려 4건을 채웠다(1건은 재시도도 실패). 실험 스크립트가 오류를 실패와 따로 세고 한 번 재시도한다.
- 같은 조건의 3회가 거의 같았다(계획 조건은 행동 수까지 같음). Jev는 같은 상태에서 거의 같은 선택을 하므로, 반복보다 작업·페이지를 늘려야 표본이 커진다.
- L1(작업 하나에 이동과 누르기가 섞임): 실패. 반품 기한은 첫 화면 "Main, navigation"에서 바로 누르기를 두 번 골라 실패 신호로 끝났다. 이동 작업과 누르기 작업을 나누지 않으면 12.7의 잘못 누르기가 그대로 나온다.
- L2(목표 요소까지 이동): 목표가 가까운 두 작업은 성공했지만 "다음"만 써서 우회가 컸다(3.2배, 1.9배). 장바구니는 "다음"만으로 34번이 필요해 작업 한도(20)를 넘었다. Jev는 시키지 않으면 제목 이동을 쓰지 않는다.
- L3(방법까지 지정): 셋 다 성공. 장바구니·반품은 최소 경로 그대로였다. 알림 설정은 "제목 단위로 Notifications까지"라고 했는데도 Jev가 "다음"을 9번 쓴 뒤에야 제목 이동을 해 16~17행동이 됐다(나머지 작업은 최소). 방법 지시도 늘 따르지는 않는다.
- `currentItem` 약점(알림을 위치로 착각)은 이번 작업들에서 보이지 않았다. 알림은 모두 마지막 작업 뒤에 나왔다.

해석: Jev에게는 "어디까지(대상과 cue)"와 "어떻게(이동 방법)"를 함께 주고, 이동과 누르기를 다른 작업으로 나눠야 한다. 계획 모델이 이 형식(L3)으로 계획을 쓰게 하는 것이 다음 질문이다. 한계: 시뮬레이터 하나, 작은 페이지 3개, 조건당 사실상 표본 1.
