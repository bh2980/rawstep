# Rawstep 로컬 대시보드 개발 계획

Rawstep 작업을 여러 모델과 프롬프트 변형으로 실행하고 비교하는 로컬 대시보드를 만든다. 사용자는 코드나 CLI 옵션을 수정하는 대신 작업, 모델 연결, 프롬프트, 환경, 허용 행동을 화면에서 관리한다. 전역 기본값과 작업별 설정을 지원하고, 각 실행에 실제 적용한 설정을 기록한다.

이 문서는 구현 범위와 검증 기준을 기록한다. `packages/dashboard`를 별도 workspace로 구성했고, shadcn 기반 UI, 로컬 Node API, 파일 저장, 실행 큐와 비교 화면, `rawstep ui`를 연결했다. 루트에서 `npm run build` 후 `npm run rawstep -- ui` 또는 `npm run dashboard`로 실행한다. 개발용 명령은 `npm run dashboard:dev`이다.

첫 완료 단위는 연결 등록부터 실제 결과 확인까지 이어지는 한 번의 실행이다. 그다음 여러 모델과 프롬프트의 실행 큐와 비교 화면을 붙인다. 최종 완료 기준은 동일한 작업을 모델 두 개와 프롬프트 두 개로 실행해 네 결과를 비교하고, 설정과 결과를 로컬 서버 재시작 후에도 다시 열 수 있는 것이다. 키보드와 스크린리더 모드는 지원하는 모델과 백엔드 조합에서 각각 확인한다.

기술 구성은 React와 TypeScript UI, Vite 빌드, 로컬 Node.js 서버로 정한다. Node 서버가 설정 파일과 기존 Runner를 다루고, 브라우저는 같은 서버의 API로 저장과 실행을 요청한다. 진행 상태는 SSE로 전달한다. React의 [직접 앱 구성 안내](https://react.dev/learn/build-a-react-app-from-scratch)와 Vite의 [백엔드 통합 안내](https://vite.dev/guide/backend-integration)를 바탕으로 구성하며, 라이브러리 버전은 구현 시점에 저장소의 Node 조건과 맞춰 고정한다.

UI 컴포넌트는 shadcn/ui로 통일한다. 앱 셸, 탐색과 페이지는 로컬 shadcn 소스로 작성한다. 같은 테마 토큰을 사용하고 `packages/dashboard/AGENTS.md`에 이후 개발에서도 shadcn을 사용하도록 명시했다.

별도 DB는 도입하지 않는다. 개발 중에는 Vite 개발 서버와 Node API를 함께 실행하고, 빌드 후에는 Node가 UI 정적 파일과 API를 함께 제공한다. 실행 명령은 현재 CLI 흐름에 맞춰 `npm run rawstep -- ui`로 추가한다.

새 workspace는 `packages/dashboard` 하나로 시작한다. 내부에 `src/web`, `src/server`, `src/shared`를 두어 UI, 파일 저장과 실행 서비스, 브라우저에서도 사용할 수 있는 계약을 구분한다. 서버는 `core`, `policies`, `browser`, `screenreaders`, `reports`의 공개 API를 사용하고 CLI에 의존하지 않는다. CLI는 `ui` 명령에서 대시보드를 로드해 실행하도록 연결한다.

현재 workspace의 빌드 순서는 [workspace.mjs](/Users/bh2980/Desktop/rawstep/scripts/workspace.mjs:4)에 명시되어 있다. 새 패키지를 추가할 때 빌드, 타입 검사, 정적 파일 복사, `rawstep` 번들(`scripts/bundle-rawstep.mjs`: 대시보드 웹 자산을 `dist/dashboard-web`으로 복사), 단일 tarball 생성, 격리 설치 검사까지 함께 수정해야 한다. UI는 `dist`나 다른 workspace의 소스 파일을 직접 참조하지 않는다.

화면 구성은 다음과 같이 정한다. 프롬프트는 작업 안에서 관리하고 전역 설정은 별도 설정 화면에 둔다.

| 화면 | 주요 내용 | 주요 동작 |
|---|---|---|
| 실험과 실행 | 선택한 작업, 모드, 모델, 프롬프트, 환경과 생성될 실행 목록 | 개별 실행, 선택 실행, 전체 실행, 중지, 새 실행으로 재시도 |
| 작업 | 기본 정보, 성공 조건, 모드별 프롬프트, 허용 기능, 환경과 고급 설정 | 생성, 기존 JSON 가져오기, 편집, 복제, 저장 |
| 모델 | 유형(LLM 또는 결정 모델), 제공자, 모델 목록, 실행 또는 분석 역할, 입력 지원과 상태 | 유형 선택, 제공자와 인증키 입력, 모델 조회, 모델 선택 |
| 실행 이력 | 결과 목록, 비교 표, 실행 설정, 단계별 기록과 스크린샷 | 필터, 상세 보기, 비교, 보고서와 데이터 내보내기 |
| 전역 설정 | 모드별 허용 행동, 실행 환경 기본값, 정책의 기본 제한 | 저장, 기본값 복원 |

실험 화면은 왼쪽에 작업 목록, 가운데에 실행 조합과 상태 목록, 오른쪽에 선택한 실행의 상세 정보를 배치한다. 좁은 화면에서는 상세 정보를 별도 화면으로 연다. Vitest UI의 선택 실행, 필터, 상세 보기 흐름을 참고하고, 시각 디자인은 명확한 타이포그래피와 충분한 간격, 절제된 상태 색으로 구성한다. 색 외에도 아이콘과 텍스트로 상태를 전달한다.

작업의 목표와 모델의 실행 지침은 서로 다른 필드로 유지한다. 목표는 무엇을 완료할지, 실행 지침은 주어진 관찰과 후보를 어떻게 판단할지 설명한다. 프롬프트 편집기에는 변경 가능한 지침과 자동으로 조립되는 목표, 이력, 후보, 관찰의 구조를 구분해 보여준다. 실행 중 관찰은 저장된 trace의 가림 처리를 유지해 표시한다.

사용자 흐름은 다음 순서로 이어진다.

1. 모델 유형(LLM 또는 결정 모델)과 제공자를 고르고 필요한 인증키를 등록한 뒤 모델 목록을 조회한다. 목록 API가 없는 제공자는 명시적인 모델 ID 입력을 제공한다.
2. 작업을 생성하거나 기존 Task JSON을 가져온다. URL, 목표, 입력값, 성공 조건과 실행 한도를 저장한다.
3. 작업의 키보드 또는 스크린리더 설정에서 프롬프트 변형과 허용 행동을 지정한다. 작업은 두 모드의 설정을 보관할 수 있고, 각 실행은 기존 Task 계약에 맞춰 한 모드로 생성한다.
4. 실험 화면에서 모델, 프롬프트 변형, 환경, 반복 횟수를 선택한다. 실행 전에 실제 조합 수와 지원하지 않는 조합의 이유를 표시한다.
5. 실행 버튼을 누르면 설정을 고정하고 큐를 만든다. 진행 중에도 기록과 중지 상태를 확인할 수 있다.
6. 결과에서 독립 검증 결과, 모델 판단, 실행 오류, 분석 상태를 확인하고 실행 간 차이를 비교한다.

새 작업 화면과 작업 편집기의 완료 확인에는 "AI로 완료 확인 제안받기"가 있다. 사후 분석 역할의 LLM 모델을 고르면 서버(`POST /api/suggest-checks`)가 시작 페이지를 헤드리스 브라우저로 열어 접근성 트리를 읽고, 모델에게 2~4개의 완료 확인을 제안받는다. 제안은 Task 계약으로 검증하고, 실행 중 변화에 의존하지 않는 규칙은 시작 페이지에서 한 번 시험해 시작 화면에서 이미 참인지 알려 준다. 페이지 구조는 선택한 분석 모델로 전송되며, 사람이 고르기 전에는 아무것도 적용하지 않는다. 모델이 쓴 `script` 규칙은 시작 페이지에서도 실행하지 않고, 코드를 읽기 전용으로 보여 준 뒤 "코드를 읽었다"는 확인을 해야 사용할 수 있다. 완료 확인은 여러 신호 중 하나로 다룬다.

저장 구조는 다음과 같이 정한다. 기존 Task JSON은 실행 계약을 유지하고, 대시보드 설정은 Task 파일과 연결해 보관한다. 현재 [Task 검증기](/Users/bh2980/Desktop/rawstep/packages/core/src/contracts/index.ts:112)는 임의의 모델이나 프롬프트 필드를 허용하지 않으므로 대시보드 설정을 그대로 Task에 넣지 않는다.

| 저장 대상 | 내용 |
|---|---|
| 기존 Task JSON | URL, 목표, 입력값, 성공 조건, 기본 모드, 단계와 시간 한도, 이동 범위 |
| `rawstep.config.json` | 스키마 버전(1), 모델(유형·제공자·모델 ID)의 비밀이 아닌 설정, 작업 파일 연결, 모드별 설정과 프롬프트 변형, 실행 프로필(허용 행동·정책·환경), 실행 환경(`machine`) |
| `.env.local` | 제공자별 인증키(사용자 지정 서버는 모델별). 대시보드 설정에는 환경변수 이름만 저장하고 UI에는 키의 설정 여부만 반환 |
| `.rawstep/experiments/<experimentId>` | 실행 목록과 상태, 설정 스냅샷, 실행별 기존 trace와 분석 및 보고서 |

설정은 공유 프로젝트 패키지 `@rawstep/project`가 소유하며 CLI도 같은 `rawstep.config.json`을 읽어 같은 설정으로 실행한다. 설정 파일은 검증 후 원자적으로 저장한다. 외부 편집이나 다른 창의 변경을 감지하면 저장 충돌을 알려 편집 내용을 보존한다. 서버가 재시작되면 완료된 이력은 그대로 읽고, 미완료 실행은 중단된 상태로 복구한다. 자동으로 모델을 다시 호출하지 않고 사용자가 새 실행으로 재시도할 수 있게 한다.

전역과 작업별 허용 행동은 다음 규칙을 적용한다.

- 전역에는 키보드와 스크린리더의 기본 허용 목록, 텍스트 입력과 값 교체 허용 여부를 저장한다. 특정 작업의 입력 이름은 전역 목록에 넣지 않는다.
- 각 작업의 각 모드는 `전역 설정 사용` 또는 `사용자 지정`을 선택한다. 사용자 지정 목록은 해당 모드의 전역 목록을 대체한다. 빈 목록과 설정 생략을 구분한다.
- 최종 허용 행동은 선택한 목록과 실제 백엔드 지원 범위에 맞춰 결정한다. UI에는 적용 가능한 행동과 지원하지 않는 항목의 이유를 표시하고 Node에서도 검증한다.
- 입력 이름의 허용 목록은 해당 작업의 입력값을 기준으로 선택한다. 텍스트 입력과 값 교체는 독립적으로 켜고 끌 수 있다.
- 허용 목록으로 모델의 후보를 생성하고, 모델이 반환한 행동도 실행 전에 검사한다. 중단 선택지, 독립 검증, 입력 필드 확인은 엔진에서 유지한다.
- 실행 시점의 전역 값과 작업 값을 스냅샷으로 고정한다. 이후 설정 변경은 이미 생성한 실행의 조건을 바꾸지 않는다.

예를 들어 전역에서는 기본 탐색과 활성화를 허용하고 텍스트 입력은 끈다. 로그인 작업은 사용자 지정으로 탐색과 활성화, `email`과 `password` 입력을 허용한다. 포커스 탐색 작업은 `Tab`과 `Shift+Tab`만 허용한다. 결과 화면에는 실제 적용한 목록과 설정 출처를 보여준다.

현재 [Runner 옵션](/Users/bh2980/Desktop/rawstep/packages/browser/src/runner/index.ts:18)은 키, 스크린리더 명령, 입력 이름의 제한을 지원한다. 입력과 값 교체를 독립적으로 제한하려면 옵션, 최종 허용 행동 계약, 후보 생성, 실행 검증을 함께 확장해야 한다. 옵션을 생략한 기존 CLI와 라이브러리 호출은 현재 동작을 유지한다.

프롬프트와 모델 연동에는 다음 변경이 필요하다.

모델 등록은 유형, 제공자, 모델 순서로 구성한다. 제공자별 모델 목록으로 입력 지원과 실행 또는 분석 역할을 확인한다. 목록에 이름만 존재하는 것으로 이미지 지원을 확정하지 않는다. 확인할 수 없는 기능은 미확인으로 표시하고 모델 ID는 직접 입력할 수 있다. 모델 ID는 실행 시작 전에 결정하고 실행 도중 임의로 교체하지 않는다. 일반 LLM 결과에는 결정 모델과 같은 확률을 만들어 넣지 않는다.

구현은 아래 순서로 진행한다. 단계마다 사용할 수 있는 결과와 검증 기준을 남긴다.

| 단계 | 구현 범위 | 완료 기준 |
|---|---|---|
| 1 설정과 기반 | 구성한 workspace와 shadcn UI 기반 위에 로컬 서버, 설정 계약과 파일 저장, 전역과 작업별 허용 행동 해석, 입력과 값 교체 제한 추가 | 재시작 후 저장한 설정이 유지되고 허용 목록이 후보 생성과 Runner 검증에 동일하게 적용됨 |
| 2 실제 한 번 실행 | 연결 등록과 SystemOne 모델 조회, 작업 가져오기와 편집, 프롬프트 저장, 키보드 실행, 진행 상태와 기본 결과 | 실제 모델이 저장한 지침과 허용 목록으로 작업을 실행하고 독립 검증 결과와 trace를 UI에서 확인할 수 있음 |
| 3 모드와 모델 확장 | 모드별 작업 편집, 모의 및 실제 스크린리더 연결 검사, 환경 편집, 일반 LLM 행동 선택, 결정 모델 연동 | 지원하는 각 경로에서 지침이 실제 요청에 반영됨. 미지원 모드나 모델은 실행 전에 이유를 표시함 |
| 4 실행 큐 | 조합 생성, 반복 횟수, 개별과 전체 실행, 취소와 새 실행 재시도, 설정 스냅샷, 서버 재시작 처리 | 작업과 모드와 환경을 각각 하나, 반복을 1회로 선택하면 모델 두 개와 프롬프트 두 개가 네 독립 실행으로 생성됨. 중지한 큐의 다음 항목이 실행되지 않음 |
| 5 결과 비교 | 실행 이력과 필터, 비교 표, 단계별 관찰과 선택, 스크린샷, 실제 설정, 선택적 분석과 중단 진단, 보고서 열기 | 실행 결과와 분석 실패를 구분하고 완료한 실험을 재시작 후 다시 비교할 수 있음 |
| 6 배포물과 검증 | `ui` 명령, 정적 파일 제공, 빌드와 패키징 반영, 브라우저 검증, 키보드 접근성과 문서 | 별도 개발 서버 없이 로컬 설치한 패키지로 UI가 열리고 전체 주요 흐름이 동작함 |

실행 큐는 첫 버전에 순차 실행으로 구현한다. 매 실행마다 정책, 브라우저와 백엔드 인스턴스를 새로 만들며 실제 스크린리더 실행이 같은 데스크톱 입력을 공유하지 않게 한다. 브라우저 화면을 닫거나 새로고침해도 Node의 실행은 유지된다. 취소는 기존 AbortSignal을 전달하고 정리와 trace 저장을 마친 뒤 최종 상태를 표시한다.

같은 작업을 실행 프로필별로 비교하는 `rawstep run <task> --profile <이름>`과 모델 및 프롬프트 실험은 구분한다. 대시보드 큐가 각각의 실행을 기존 Runner로 수행하고 결과를 묶는다. 기존 분석과 보고서 생성기를 재사용하며 같은 작업의 실행 한도, 환경, 허용 행동이 비교 표에서 확인되도록 한다.

서버 API는 설정 읽기와 저장, 작업 읽기와 저장, 연결 검사와 모델 조회, 실험 조합 계산, 실행과 취소, 이력과 산출물 조회, 상태 이벤트 전송을 제공한다. 상태 이벤트는 저장된 trace와 큐 상태를 기반으로 하며 재연결 시 누락된 순서를 복구한다. PNG는 이벤트마다 반복 전송하지 않고 산출물 참조로 조회한다. 서버는 loopback에 바인딩하고 요청 Origin과 프로젝트 파일 경로를 검증한다.

실행 기록에는 해석된 Task, 모드, 백엔드와 모델 식별자, 프롬프트 지침과 버전, 후보 문구의 버전 또는 해시, 최종 허용 행동, 환경, 정책 제한과 반복 번호를 보관한다. 인증키와 입력의 실제 값은 내보내는 실행 설정에 포함하지 않는다. 실행 상태, 원래 결과, 분석 상태와 보고서 생성 상태는 별도 필드로 유지한다.

이력에서 새 실행을 만들 때 비밀이 아닌 설정은 기존 스냅샷을 사용하고 입력값은 작업 파일에서 다시 읽는다. 작업 파일이 변경되면 차이를 표시하며 과거 trace에서 가려진 입력값을 복원하지 않는다. 재시작 전 생성한 실행은 메모리에 고정한 입력값으로 진행한다.

검증은 구현의 주요 경계에 맞춰 진행한다.

- 설정 저장과 다시 읽기, 전역 상속과 작업 대체, 빈 허용 목록, 작업에 없는 입력 이름, 지원하지 않는 행동을 검사한다.
- 입력과 값 교체의 네 가지 조합을 검사하고 금지한 동작이 후보와 실제 실행 양쪽에서 차단되는지 확인한다.
- 모델 목록 조회와 입력 지원 판정, 키의 비노출, 모델 ID 고정, 프롬프트 전달과 버전 기록을 검사한다.
- 실행 조합 수, 각 실행의 인스턴스 분리, 실행 중 설정 변경, 취소, 분석 실패, UI 재연결과 Node 재시작을 검사한다.
- 기존 CLI와 라이브러리의 기본 동작에 대한 회귀 검사를 유지하고, 새 UI 패키지의 빌드와 정적 파일을 포함한 격리 설치를 확인한다.
- 브라우저에서 연결 등록, 작업 저장, 허용 기능 설정, 한 번 실행, 전체 실행, 중지, 결과 비교와 재시작 후 이력 확인을 끝까지 수행한다. 자동 검증에는 결정 가능한 테스트 어댑터를 사용하고 실제 추론과 구분한다.
- 실제 모델로 대표 흐름을 추가 확인하고, 네이티브 VoiceOver, NVDA, Orca 검증은 대응 환경에서 수행한 결과만 기록한다. 모의 실행을 네이티브 검증으로 표현하지 않는다.
- UI 자체의 키보드 이동, 포커스, 필드 레이블, 오류와 진행 상태 안내, 읽기 쉬운 표, 상세 패널과 작은 화면을 확인한다.

첫 버전 완료 이후에는 브라우저 실행의 동시성, 공유 프롬프트 템플릿, 후보 설명문 편집, 로컬 모델 서버의 실행과 재시작 관리, 장기 실험 추세를 확장할 수 있다. 초기에는 외부 모델 런타임의 상태와 실제 설정을 표시하고 사용자가 준비한 서버에 연결한다.


## 구현과 검증 기록 (2026-10-05)

- 설정·Task 파일의 외부 수정은 함께 revision에 반영하고 저장 및 실행 전에 충돌을 검사한다. 전역 상속, 작업 대체, 빈 허용 목록, 입력과 값 교체의 네 조합을 후보와 실행 검증 양쪽에서 확인했다.
- 실제 Chromium과 HTTP 테스트 응답으로 두 모델 × 두 프롬프트의 네 독립 실행, LLM 행동 선택, 모의 스크린리더 실행과 보고서 생성을 확인했다. 자동 테스트의 응답은 실제 추론이라고 표시하지 않는다.
- 브라우저에서 전역·작업 허용 기능 저장, 작업 생성과 목표 편집, 모델 조회·등록, 네 실행과 결과 비교, 기존 조건 재실행과 20개 큐 중지를 확인했다. 이력과 전역 설정 화면의 axe 검사에서 위반 0건을 확인했고, 390px 화면의 가로 넘침과 키보드 첫 포커스도 확인했다. 서버 종료 후 재시작한 이력과 설정은 API 검사로 확인했다. 완료된 기록에는 설정 당시 스냅샷을 유지한다.
- 격리 npm 설치 검사에서 대시보드를 포함한 여덟 패키지의 의존성과 공개 import, UI 정적 파일, API 저장 후 재시작을 확인했다. npm 게시 자체는 수행하지 않았다.
- 실제 설정된 SystemOne HTTP `jev-1.13.0`로 버튼 활성화 작업을 실행해 독립 검증 성공과 분석·보고서 생성을 확인했다. 발화 관찰은 모의 VoiceOver이며 네이티브 스크린리더 증거가 아니다. 기록은 `.rawstep/dashboard-real-model-5516cf53-af6a-4824-abfa-069d35461e4c`에 보관했다.
- UI는 모의 VoiceOver, VoiceOver와 NVDA 연결을 제공한다. Orca는 기존 CLI/API 경로를 유지한다. 네이티브 VoiceOver·NVDA·Orca의 실제 발화 검증은 준비된 대응 환경에서만 수행하며 이번 대시보드 검사에서 완료했다고 주장하지 않는다.

작업 화면은 개요(페이지에서 되풀이된 문제와 모델이 헤맨 지점), 완료 확인 편집기, 설정으로 나누고, 실행 화면은 행동마다 점을 찍은 타임라인과 선택한 행동 하나를 보여 준다.
